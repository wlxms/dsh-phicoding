# design-gain

判断一个抽象该留还是该撤，不靠感觉，靠**每个变体的实测代价**。

## 记什么

对每个已经加过的变体：

```markdown
| 变体 | 主干改动（字节哈希 / 行） | 非主干改动 | 断言证据 |
| --- | --- | --- | --- |
| #1 第三个来源 | 0（SHA256 未变） | +? 行 | 场景 5 绿 |
| #2 客户端材质化 | 0（SHA256 未变） | +43 行 | 场景 6a-6d 绿 |
```

**主干改动要能一条命令复核。** 先把主干声明为字节可比的边界（见 `design-ladder`），比对 SHA256。"大概改了几行"不是证据。

## 判据：脚手架还是收费站

- 加第 N 个变体的成本**随 N 递减并趋于常数** → **脚手架**。抽象成立，留着。
- 成本**随 N 递增** → **收费站**。每过一个变体都要交一次钱。
- 成本**恒为 0 但没人用** → 不是收益，是**冗余**。按准入律撤掉。

收费站不用等大重构才发现——**第 3 个变体上就能感觉到**。

## 三种结论

| 观察 | 结论 |
| --- | --- |
| 成本递减 / 恒定，且有 ≥2 个真实变体 | **留**。这是脚手架 |
| 成本递增 | **改**：先归类（同轴新变体 / 正交新轴 / 用例集扩张），修扩展点而不是打补丁 |
| 成本为 0 但没有第二个具名变体 | **撤**：退回最简实现 + `ponytail:` 标记缝 |

## 撤的代价是真的

撤抽象比去重复难得多：依赖已经建立，契约已经被人依赖。所以：

- 没有实测成本数据时，**不要**凭"感觉太复杂"去撤。
- 撤之前先问：**它有没有让某条必须支持的用例变得不可达？** 有 → 那不是该撤，是该改。
- 撤的判据只有一条：**它破坏了灵活性** —— 也就是加新变体的成本在递增，或者新变体必须动主干。
