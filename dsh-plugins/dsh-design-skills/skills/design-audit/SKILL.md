# design-audit

只读。不改代码，只出发现。范围可以是一个改动，也可以是一个仓库。

## 五个红灯（按严重度）

1. **主干源码里出现变体的名字或变体专属字段。** 主干在管理它本不该认识的东西。
   → 改为注册表 / 契约发现，主干只引用契约。
2. **扇入型接口上放了变化点。** 被很多调用者使用的接口被当成扩展点。
   → 冻结形状；变化点挪到扇出方向上。
3. **接口只有一个实现，且说不出第二个具名变体。** 变异驱动的投机接口。
   → 删掉，退回最简实现 + `ponytail:` 标记缝。
4. **两个分支的流程图**形状不同**却被硬凑成一个框架。** 那不是两个变体，是两件事。
   → 拆开，或在上层找真正的公约数；诚实的话就是两个实现加一层薄门面。
5. **N 个布尔开关组合出行为空间。** 那不是"分支太多"，是 N 个尚未找到轴的决定。
   → 消掉开关；每个开关背后都有一根未命名的轴。

## 输出格式

每处一条，三列，**按"最大削减优先"排序**：

```markdown
| 位置 | 删什么 / 改什么 | 换成什么 |
| --- | --- | --- |
| Engine/Contracts.cs:41 | 主干读的 `kind == "atlas"` 分支 | 注册表按 kind 查，主干只持契约 |
| Host/... | 只有一个实现的 `IContentTransformer` | 删；装饰器形状已够，`ponytail:` 记下缝 |
```

没有发现就明说"未发现过度抽象"，不要为了凑数报无关的风格问题。

## 不要报的

- 命名、格式、注释风格 —— 那不是本轮的问题。
- 你还没读懂就报的"太复杂"。**先读完再懒**：跳过理解去报一个漂亮的发现，是把无知包装成效率。
- 用户明确要求的复杂度。他要求了就是需求，不是过度设计。

## 与 `design-debt` 的分工

本技能找**现在已经错了的**；`design-debt` 盘**当时故意留的缝**。前者是缺陷，后者是账。不要把缝报成缺陷。
