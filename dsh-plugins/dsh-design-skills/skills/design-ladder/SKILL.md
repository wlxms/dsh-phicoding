# 阶梯用例与可证伪验证

## 五个档位 + 一档组合

| 档 | 定位 | 说明 |
| --- | --- | --- |
| L1 | 最小循环 | 三集里的**最简流程**就是 L1 |
| L2 | 主扩展 | 在 L1 之上叠加主路径的典型变化 |
| L3 | 边界 | 边界值、边界条件、组合边界 |
| L4 | 容错 | 非法输入、异常、降级路径 |
| L5 | 集成 / E2E | 跨模块、真实环境端到端 |
| **组合** | **设计级专用** | **用现有抽象拼一个需求没列举的行为**。拼不出来 = 核心抽象不够底层，回去重抽 |

组合档是把"图灵完备性"从不可证伪的想象变成可执行测试的唯一办法。

## 设计规则

1. 每档三列写清：输入 / 期望 / **它强制新增的实现或容错**。
2. **说不出「它逼出了什么」的档位 = 投机用例，删掉。** 同一条律在设计侧的形态就是准入律。
3. **L1 是红基线锚点**：先确认它在当前代码下确实失败。无法自动验证时给出人工复现步骤。
4. 假设边界之外的场景不设档 —— 边界外一律不做，无需用例辩护。
5. 每一处防御（判空 / 容错 / 日志 / 开关 / 抽象）都必须有一个让它存在的失败用例，默认全部不加。

## 可证伪：先声明边界，再测字节

**谈「改了几行」之前，先把主干声明为一个字节可比的边界**（哪几个文件 / 哪几个目录），把基线冻下来，扩展前后逐字节比对。

行数是含糊的——算不算注释、算哪个目录都能吵。SHA256 不吵。

```
主干 = Engine/（2 个文件）
基线 = _baseline/（SHA256 已记录）
变体 #2 之后：Engine/*.cs 与 _baseline 逐字节比对 → 改动 0 行
```

## 必须与断言配对

**主干 0 行 ≠ 性质成立。** 实战里出现过：主干 diff 为 0、抽象形状正确、编译通过、三档用例全绿，而一个一行的实现细节（暂存构造里把缓冲清零，抢在校验之前毁掉崩溃残留）静默杀死了核心性质——**只有一档用例抓住它**。

所以预言与实测缺一不可，而且收尾必须有一行**失配记录**：

```markdown
## 结果 · 第 N 轮
- 预言：变体 #2 改主干 0 行
- 实测：主干 0 行（SHA256 逐字节相同）
- 断言：场景 3 绿 —— 崩溃残留被回读校验后直接提交，零重下
- 失配：无  |  或：预言 >0 实测 0 —— **被证伪的是我的预言**
- 刻意未覆盖：…
```

预言被证伪时，把它写成发现，不要抹平。那通常是这一轮最值钱的输出。

## 失败分类（禁止改断言求绿）

| 分类 | 含义 | 去向 |
| --- | --- | --- |
| 产品缺陷 | 实现不符合用例期望 | 修实现 |
| 用例陈旧 | 用例描述的是旧语义 / 已被推翻的假设 | 回设计卡修正，写明理由 |
| 环境问题 | 夹具 / 依赖 / 基础设施 | 说明环境因素与绕过方式，不计入实现正确性 |

## 方向判据：脚手架还是收费站

加第 N 个变体的成本**随 N 递减并趋于常数** = 脚手架；**随 N 递增** = 收费站。收费站不用等大重构，第 3 个变体上就能感觉到。见 `design-gain`。
