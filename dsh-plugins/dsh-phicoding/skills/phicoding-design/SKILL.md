# phicoding-design

## 找准主干（设零）

> **最小框架 = 能实现功能的最小实现载体。**

先回答：**这个功能的最小实现是什么？** 不是"最简版本"，是"构成它、少一个就不成立的那几个环节"。

**最小实现的每一个环节，对应一个底层抽象。** 环节数 ≠ 抽象数——一个环节可能不需要抽象（写死数据），两个环节可能共用一个抽象（同一个累积器用在两处）。

反例：给一个**写死的东西**抽接口——固化层不配接口。**判据不是"有几个实现"，而是"它属于哪一层"**：可替换层配接口，固化层写死，可新增层走组合。

> 一个实现也照样配接口。接口是公开面，公开面由**是不是公开**决定，不由**有几个实现**决定——见 `phicoding` 的接口节。

## 程序的工作是解释

> **程序的职责，是把策划的想法翻译给计算机。**

策划的想法天马行空，**每一个想法都要先被解释一次才能跑起来**。这就是拓展性必须排第一的原因——不是审美，是解释会源源不断地来。

**Type Object（类型对象）不改变这件事。** 它让策划在表里加一个种类，但那个种类只有在代码已经会解释它时才跑得起来。它扩大的是"谁能表达"和"要不要重编译"，**不是"能表达什么"**——策划的自由度 = **既有解释的组合**。

所以类型对象的位置是**载入边界**，不是主干：

```
config    { "kind": "one-hand-sword", "bonus": [...] }   ← 名字可以在这里
              ↓  工厂：名字 → 类型的唯一位置
工厂      Kinds.Add("one-hand-sword", new OneHandSword());
              ↓
类型      sealed class OneHandSword : Weapon { }          ← 结构、行为、归属全在这里
              ↓
主干      item.Kind is OneHandSword                       ← 主干里没有名字，只有类型
```

| 谁 | 回答什么 |
| --- | --- |
| **config** | "这是什么"（**可以出现名字**）、"数值是多少" |
| **类型** | "怎么运作"、"占哪里"、"属于谁" |
| **工厂** | 名字 → 类型。**唯一允许出现名字分派的地方** |

## 度量：新增一个解释的成本

这是设计是否成立的**唯一度量**：

> **新增一个"解释"，要写几处代码、要理解多少东西？**

| 要做的事 | 目标成本 |
| --- | --- |
| 组合既有解释（加一个实例、改数值） | **0 处** |
| 新增一个解释（一个新概念） | **一个类型 + 一行登记** |

目标还包括：**读完一个已有解释就能照抄出下一个**，不需要理解主干内部。

由此推出三条：

1. **每个扩展点必须有一个可照抄的样板**——读完一个实现就能写出下一个
2. **扩展点与主干之间只允许一个窄缝**（一张登记表）。出现第二个缝，就是分层错了
3. **新增一个解释若需要动到两处以上**，或需要先读懂主干——那是分层错了，不是写的人笨

**第 2 条的常见破法：自登记 + 别处的触碰清单。**

一个"自登记"的类型（在静态构造或私有构造里往工厂登记）本身是一个缝。但如果它**只有被触碰才会登记**，就还需要一份"逐个触碰"的清单——那是第二个缝。

漏掉它的后果不是报错，是**静默不登记**：那个变体连同它所有的数据行一起消失，检查表里也看不到它。

| 做法 | 缝的数量 |
| --- | --- |
| 类型自登记 + 别处逐个 `register()` 去触发 | **2**（类型清单与触碰清单必须同步） |
| 一张工厂文件里列出全部 `Add("name", new Xxx())` | **1**（改一处即可） |

**一处陷阱**：如果"加一个新概念"看起来只花了 0 处代码，先别高兴——那通常说明**这个概念没有携带任何行为**，它只是既有解释的又一次组合。要问一句：策划真正想要的效果，config 里表达得出来吗？

## 装载诊断：报错和警告，但不抛异常

策划与程序**并行开发**。策划先写了 `"kind": "axe"`，程序还没写 `Axe`——**这是正常状态，不是故障。**

正确的模型是**编译器**：config 是源码，未登记的种类是未定义符号。编译器遇到未定义符号不会 abort，它报一条、继续、最后汇总。

| 情况 | 级别 | 处理 |
| --- | --- | --- |
| 引用了未登记的种类 / 需求种类 | **警告** | 等一等会好。跳过该条目，继续装载 |
| 重复 id、引用了不存在的 id、数值非法 | **错误** | 等多久都不会好。跳过该条目，继续装载 |
| 文件读不了、语法错 | **异常** | **唯一该抛的地方**——框架自己无法继续 |

两条硬要求：

- **报告必须指名**：缺的是哪个名字、哪一条数据引用了它。只说"数据有误"没有价值。
- **不产出半成品**：未解释的条目就是**不存在**。不要造一个"未知种类"的占位对象让它半死不活地占着位置——那比缺一个条目更糟。

装载期与查找期是两回事：**装载期不抛，查找期可以抛**。装载期是"数据里有个还没解释的东西"（正常），查找期是"你问了一个不存在的东西"（调用方的错）。

## 设计哲学

| # | 准则 | 落地形式 |
| --- | --- | --- |
| 0 | 找准主干、最小框架、最小抽象 | 见上 |
| 1 | **以拓展性为先** | 拓展时使用者不破坏主干。判据：加一个变体，主干 diff = 0 行 |
| 2 | **以编码安全 / 强制性为先** | 好的框架约束使用者，在给定范围内提供灵活性。把运行期的隐式失败变成注册期 / 编译期的显式失败 |
| 3 | **最小信息成本** | 抽象、接口、参数只使用满足需求的最小信息 |
| 4 | **信息有边界** | 主干不知道实现；实现不默认其他实现存在（除非同一体系内）。组合关系必须用 `[Require]` 显式标注 |
| 5 | **核心框架应完备** | 设计之初就有足够灵活性支持该领域任何拓展——**靠可组合，不靠功能齐全** |

## 设计规范

1. **先思考最小实现，基于最小实现的可变性设计框架。** 每个底层抽象代表最小实现的某个关键要素/环节。
2. **按可变性三层拆解**：

| 层 | 内容 | 处方 |
| --- | --- | --- |
| **固化** | 主干语义、顺序、不变量 | **写死，不动** |
| **可替换** | 同一位置的多种实现 | **接口 + 抽象类**：接口是最小公开面（唯一可注入的），抽象类放共享实现 |
| **可新增** | 往集合／顺序里加成员 | **组合** |

3. **明确最小信息**：主干只能知道抽象——**主干出现任何实现的类型或字段都是严重错误**。实现不能拥有其他实现的信息，除非组合；组合也必须 `[Require]` 标注。
4. **类型替代枚举**：枚举只用于单个方法内的简单分支；任何方法之外的多类抽象都用类型。
5. **面向用户类型安全**：使用者面对的是类型安全的接口（**不得是具体抽象**），参数尤其如此。框架内部不直接对外的部分可以用 `object as T`。
6. **可以新增抽象来实现功能，不能修改抽象来实现新功能。**
7. **接口是最小的公开面**——所有公开面必须被一个以上的接口覆盖；每个抽象至少配一个接口，且接口覆盖它的完整抽象面；**依赖注入只能注入接口**。见 `phicoding` 的接口节。

规范6 与设零的关系：**"修改抽象"和"换一个正确的抽象起点"是两件事。** 若需求里已明确"本领域会有未知维度"，那么能承载未知维度的抽象才是"能实现功能的最小载体"——那是设零在起作用，不是违规。

## 设计顺序

```
1. 最小实现是什么？            → 拆出环节，每个环节一个抽象（或明确不需要抽象）
2. 每个环节的可变性在哪？      → 固化 / 可替换 / 可新增，三选一
3. 主干知道什么？              → 只允许知道抽象；出现实现类型即返工
4. 公开面是什么？              → 只留完成功能所必需的方法与参数
5. 使用者被怎么约束？          → 把隐式失败提到注册期或编译期
```

## 一个完整的推导示范

需求：一个技能释放管线，环节可增删、每个环节可换实现。

- **最小实现**：一个值从一端进、按顺序经过若干变换、从另一端出。三个环节：**环节 / 顺序 / 传递**。
- **固化**：顺序执行语义（主干，写死）。
- **可替换**：`Pass<T>` 的实现 → 继承与多态。
- **可新增**：`Add` 新环节 → 组合。

关键一步是让**管道自己也是一个环节**：

```csharp
public abstract class Pass<T>
{
    public abstract T Run(T input);
}

public sealed class Pipe<T> : Pass<T>
{
    private readonly List<Pass<T>> passes = new();

    public Pipe<T> Add(Pass<T> pass)
    {
        passes.Add(pass);
        return this;
    }

    public override T Run(T input)
    {
        for (int i = 0; i < passes.Count; i++) input = passes[i].Run(input);
        return input;
    }
}
```

`Pipe<T> : Pass<T>` 这一行让分组、复用、分段全部变成组合，主干零改动。条件与中断也不再需要新机制——**在框架之外新增一个 `Pass<T>` 子类**即可：

```csharp
public sealed class Branch<T> : Pass<T>
{
    private readonly Func<T, bool> test;
    private readonly Pass<T> yes;
    private readonly Pass<T> no;

    public Branch(Func<T, bool> test, Pass<T> yes, Pass<T> no)
    {
        this.test = test;
        this.yes = yes;
        this.no = no;
    }

    public override T Run(T input)
    {
        if (test(input)) return yes.Run(input);
        return no.Run(input);
    }
}
```

**有分支，零 `else`。** 「提前结束」也不需要主干支持：`new Branch<T>(t => t.Done, new Pipe<T>(), rest)`。

这就是设5 的实现方式：**完备性来自可组合，不来自功能齐全。**
