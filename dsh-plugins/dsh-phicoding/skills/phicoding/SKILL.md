# phicoding

一句话锚：**最小完备，信息单向。**

- **最小完备** —— 最小实现（核2）与能力完备（核3）是对立的。解法只有一个：**完备性靠可组合达成，不靠把功能做进去。** 固化写死、可替换走继承与多态、可新增走组合。
- **信息单向** —— 依赖图不得有环。由此产生信息等级：高等级可取低等级的信息，反之不可。
- **解释** —— 程序的职责是把策划的想法翻译给计算机，而想法会源源不断地来。因此设计是否成立的**唯一度量**是：**新增一个"解释"要写几处代码**。目标是一个类型 + 一行登记。

## 核心哲学（序号即优先级，序号小的压序号大的）

1. **以人为本** —— 简单清晰易读 > 高性能。
2. **最小实现** —— 方法、设计、框架，核心都是一套完备的最小实现，不多发散。
3. **能力完备** —— 无论方法、框架、实现还是设计，都以完整、完备的方式结束。
4. **最小最简命名** —— 避免前缀后缀。除非名字本身不通用或不唯一（`Single` 已被 LINQ 占用 → 用 `Singleton`）。
5. **最小公开** —— 只公开完成功能所必需的信息、接口与参数。**接口是最小的公开面**（见下节）。
6. **依赖单向** —— 严禁互相依赖。
7. **低耦合高内聚** —— 一个方法实现其完整内聚功能，除非该功能可拆为子功能做编排，否则不拆。方法过长过大则重新抽象。
8. **TDD** —— 只保证核心业务的核心需求与小范围鲁棒性，不做过多容错。

**冲突按序号判。** 核5 与核1 冲突时核1 胜。核3 与核8 冲突时核3 胜——但"异常向外传播"本身就是一个完备且已定义的语义，不算不完备。

## 编码哲学

1. **代码即注释** —— 能不写就不写。
2. **注释可追溯** —— 必须有作者、日期、原因。
3. **命名简单直接** —— 用软件工程用词，避免生僻词。
4. **线性直达无分支** —— 从上到下自然线性，避免 `else`。**early return 表达不了时，不是回头写 else，而是反思这个方法是否该重新抽象。**
5. **设计模式优先** —— 需要穷举时用设计模式，而不是堆 `if` / `switch`。

## 接口：最小的公开面

> **接口是最小的公开面——一个层级里能被公开的东西，最底下那一档就是接口。**

它只含能力面，不含固化与身份，所以**承诺最少、能被最多人看见**。同一个根管三件事：

| # | 推论 |
| --- | --- |
| 1 | **所有公开面必须被一个以上的接口覆盖** |
| 2 | **每个抽象至少配一个接口**——接口覆盖它的完整抽象面 |
| 3 | **依赖注入只能注入接口**——不得注入具体抽象 |

**2 与 3 是 1 的推论，不是三条独立规则。** 抽象是公开面，所以要被接口覆盖；注入是一种公开，所以注入面只能是接口。

由此得到接口的等级：**接口必须定义在所有使用者的等级之下**——这就是"最底层"的判据形态。

**接口命名不在本体系规定范围内。** 是否加 `I` 前缀，是语言生态与核1 / 核4 之间的取舍，由实现者定，不构成违规。

## 边界：管编码与设计，不管实现

> **这套哲学处理「怎么写」与「怎么切」，不处理「怎么实现」。**

| 层 | 管不管 | 管什么 |
| --- | --- | --- |
| **编码** | **管** | 命名、分支、注释、模式优先 |
| **设计** | **管** | 主干、三层拆分、依赖方向、类型替代枚举、拓展性 |
| **实现** | **基本不管** | 数组还是字典、重算还是记增量、缓存不缓存 —— **都行** |

**唯一伸进实现层的一只手：不得采用明显高开销的做法。** 例如：

- 在 `Update` 里调反射
- 该用字典的地方做成线性遍历

**边界之外的差异不是违规，是选择。** 两个代理一个选重算、一个选记增量，**都合格**——检查器不许为此报警，评审也不许把它写成"违规"。

热路径的高性能实现**仅限于框架内部**，而且一样要用足够优雅的写法；低频调用可以用性能换易用性与便捷。

## 硬约束（可机械判定）

> **核心规则不能只活在专项技能里。** 会决定成败的规则必须随本技能必到——专项技能可能被合理地跳过，而跳过它的理由听起来通常很有道理。

| 约束 | 判据 |
| --- | --- |
| No Else | 源码里搜不到 `else` |
| No Switch | 源码里搜不到 `switch` |
| 类型替代枚举 | 抽象层面无 `enum`（枚举只允许出现在单个方法的简单分支内） |
| 主干只知抽象 | 主干里声明的类型**不引用主干之外**的类型（`0900`），也不引用同一族里更具体的类型（`0750`） |
| 不写注释 | 除 `// [作者 日期] 原因` 追溯记录外搜不到注释 |
| **依赖无环** | **主干里出现 `A → B → A` 即违规。别靠肉眼判断**——跑 `phicoding --root <项目>`，有环 exit 1 |
| **抽象配接口** | 每个 `abstract class` 至少实现一个接口 |
| **命名合范式** | 接口 `I` 开头 · 枚举 `E` 开头 · 特性 `Attribute` 结尾 · 异常 `Exception` 结尾 · 扩展类 `Extension(s)` 结尾（只扩展一个本工程类型时，还要以那个类型开头） |
| **引用不越档** | 引用了 B，就不许再引用同一族里比 B 更具体的类型：**接口档只认接口，抽象档只认抽象，具体档不认可子类** |

## 路由

| 你现在要做的事 | 加载 |
| --- | --- |
| 设计框架 / 抽象 / 分层 / 决定该不该抽 / config 与类型的分工 / 装载报错策略 / 新增一个解释要写几处 | `phicoding-design` |
| 判断谁能看谁、注入太深、底层要依赖上层 | `phicoding-level` |
| 写注册表 / 事件 / 管线 / 管理器 | `phicoding-shape` |
| Unity 组件与生命周期 | `phicoding-unity` |
| 审规划、审交付（哲学法官的两个关口）、收尾自审 | `phicoding-check` |

## 流水线：规划 → 审规划 → 执行 → 硬检查 + 软审查

> **规划和执行之间必须有一道闸。** 规划错了，执行越努力越远。

```
设计者     产出规划：最小实现、三层拆解、三条链路、锚点、设计模式
   ↓
哲学法官   关口一 · 审规划 —— 不通过不许开工
   ↓ 通过
执行者     按已批准的规划写代码
   ↓
哲学法官   关口二 · 先跑硬检查，再补软审查
   ↓ 通过
收下
```

> **本插件不自改。** 流水线里发现的问题改的是工程代码；技能本身只在维护者决定时更新，
> **不由某一轮回写**。让每一轮的临时发现都能进住常驻资产，就是污染的开始。

**哲学法官是一个角色、两个关口**——审规划的人和交付后审代码的人是同一个。合并的理由很简单：**它们做的本来就是同一件事，只是发生的时机不同。**

| 角色 | 谁 | 必须加载 |
| --- | --- | --- |
| **设计者** | 主智能体，或独立子智能体 | `phicoding-design` |
| **哲学法官** | **独立子智能体**——不能是设计者本人，也不能是执行者本人 | `phicoding-design` + `phicoding-check` |
| **执行者** | 独立子智能体 | 按规划指定的技能 |

规划可以由主智能体自己做，也可以派子智能体做；**但审它的那个必须是独立上下文。**

### 关口一：规划合不合哲学

规划缺任何一件，打回：

1. **最小实现**是什么——拆成哪几个环节
2. **固化 / 可替换 / 可新增**各自是什么
3. **依赖链路**——谁依赖谁、方向如何
4. **替换与拓展链路**——新增一个"解释"要动哪几处（度量：一个类型 + 一行登记）
5. **锚点**——执行期间**不许动**的东西
6. **设计模式**——用了哪个，以及**为什么不是另一个**

**锚点** = 固化层 + 主干契约 + 度量目标。**锚点必须能被判**：写不成一句可机械判定的断言，那就不是锚点，是愿望。

**锚点必须落到断言。** 规划里每条锚点都要写出"它将被哪条断言守住"；交付时每条锚点都要能找到守它的那条断言。

> 找不到的那条锚点，要么**不够具体**，要么**根本没被执行**——两种都必须当场判出来。

于是流水线与这一族技能的主线接上了：**规划定锚点 → 锚点变断言 → 断言被变异测试。**

审规划的清单在 `phicoding-check`。

### 关口二：硬检查 + 软审查

> **作者审自己，验的是"我以为我写的"，不是"我实际写的"。**

代码写完**不算完**。把 **代码 + 需求原文 + 作者自己的报告**交给哲学法官，并明确告诉它：

> **作者的结论是"声称"，不是证据。**

**第一步永远是硬的。** 先跑检查器：

```
phicoding --root <项目>
```

红了就是违规，直接打回，**没有讨论空间**——这一步没有判断余地，所以也不该由人来判。

**硬检查覆盖不到的，才由软审查做。** 硬检查只认结构与语法：

| 硬检查（检查器）管 | 软审查（智能体）管 |
| --- | --- |
| 主干有没有 `else` / `switch` / `enum` | **行为对不对**——业务算得对不对、需求满足了没 |
| 命名粒度 | **主干找对了没**——最小实现是不是真的最小 |
| 依赖有没有环、有没有向上边 | **作者漏了什么**——它列的检查清单本身就是缺口地图 |
| 注释格式、按字符串分派 | **分辨违规与实现选择**——实现方式不同不等于违规 |

**软审查做四件事：**

1. **独立复跑**——自己跑 `phicoding`、自己跑工程测试、自己数数字。作者的"全绿"必须自己重现一次
2. **变异测试行为层**——结构层已在框架里测过（不归业务项目）；**行为层要人做**：往核心不变量里注入一个坏值，看工程测试会不会红
3. **找作者没检查的东西**——缺口比错误值钱
4. **对账锚点**——规划里的每条锚点，交付时有没有一条断言在守它

一个角色两个关口，详细清单都在 `phicoding-check`。

## 硬性检查：一条命令

能机械判定的部分已经做成检查器。**写完代码就跑，不要靠自觉。**

```
phicoding --root <项目目录>             跑全部
phicoding --list --root <项目目录>      列规则
phicoding --list                        列出规则（从目录扫，不手写清单）
```

**项目侧准备一样，一次配好：**

| 文件 | 内容 |
| --- | --- |
| `<项目>/.phicoding/config.json` | 主干在哪、变体在哪、注释策略、作者、规划文件 |

**不再需要 `levels.json`。** 它原来要回答"谁在谁上面"，而这件事现在由两条**本地**规则回答：`0900` 看每条引用两端各自声明在哪个目录，`0750` 看每条引用两端各是什么档位。两张判据都不需要一张全局等级表。

**谁在什么时候跑**：执行者交付前 · 哲学法官关口二 · 任何人复跑时。
**红了怎么办**：看 `phicoding-check` 的「规则清单」——每条规则对应一种改法。

### 已有工程：只判这次动过的

一个既有工程早就违反了一堆原则。全量判就是全红，而全红的报告等于没有报告。这时用会话范围：

```
phicoding --root <项目目录> --session-begin   开工第一条命令，拍基准
phicoding --root <项目目录> --diff            只把这次改动范围内的违规算红
```

| 颜色 | 含义 | 挡不挡 |
| --- | --- | --- |
| **红** | 这次改动范围内出现违规，或新增了环 | **挡** |
| **灰** | 文件改过，但不在本会话的动作账里（很可能是别的 agent 干的） | 不挡，列出来 |
| **软** | 改动范围外的既有违规 | 不挡，只计数 |

**退让的只有历史，不退让增量。** 一行被改过，那一行的历史豁免立刻失效——所以"旧文件"这个概念不存在，只有"没被碰过的行"。

**摘要里必须看到 `(scope)` 和 `红/灰/软` 三个数。** scope 模式的 `OK` 与 strict 的 `OK` 不是同一句话：前者是"没变坏"，后者是"合规"。看不出区别，就等于又一种假绿。

## 两条豁免落在同一个位置

| 豁免 | 允许的位置 |
| --- | --- |
| 用 `object as T` 擦除类型 | 最低等级的框架内部 |
| 做高性能实现 | 最低等级的框架内部 |

最低等级不为任何具体实现负责，所以它可以擦类型（换通用）、也可以换实现（换速度）。一旦升到用户面，两条同时失效——**用户面必须类型安全、必须优雅、不得为性能牺牲可读**。

**高频才优化，且要有依据**：默认写最小实现，测出热路径再换内部实现。低频路径可以用性能换易读——例如订阅时复制数组，换派发时零分配。

## 注释的唯一格式

只在**破坏编码哲学**时写注释：临时处理、特殊处理、主干需要硬编码判断某个实现。

作者取**版本管理的用户名**；**没有版本管理就用系统用户名**（$env:USERNAME）。日期用当天。

```
// [Administrator 2026-10-10] 这里硬编码了 Atlas 类型，因为打包期才能确定落盘摘要
```

**方括号里是可解析的部分**（按空格切：作者、日期、然后只能是 `key=value`），
**方括号外整段是原因**——随便写，引号、逗号、`items[0]` 这样的方括号都不用转义，
因为它不再是"某个字段的值"。可解析的进括号，人话留在外面。

```
// [Administrator 2026-10-18 waive=0650 why=serialization] 线格式里的 type 字段，反序列化必须读
```

| 在括号里 | 必填 | 说明 |
|---|---|---|
| 第 1 项 `作者` | 是 | 必须等于项目作者 |
| 第 2 项 `日期` | 是 | `YYYY-MM-DD` |
| `waive=<规则id,...>` | 按需 | 逗号分隔的规则 id：这些规则对**这条注释所在的成员**不生效 |
| `why=<类别>` | 有 `waive` 时必填 | 豁免属于哪一类：`data` / `serialization` / `plumbing` |

**字段表是封闭的。** 不认识的键直接报错——否则拼错的键会静默失效，而那条注释看起来完全合规。
